Client-side versus server-side processing

By the end you can…
  • Client-side JavaScript can offer immediate feedback and responsive interfaces, but its validation can be bypassed or altered.
  • Server-side code enforces permissions, validates input against business rules and updates authoritative records or databases.
  • Processing choices trade off device load, server load, confidentiality, latency, accessibility and reliability; many systems use both.

Follow the reasoning

BROWSER: check form age is a number.
POST /booking with date and seats.
SERVER: authenticate, validate, check stock,
transactionally store booking.
SERVER → response with booking result.
BROWSER → display accessible confirmation.

I DO · MODEL

Why must a server check a submitted quantity even if the browser requires 1–5?

Client: input min=1 max=5
Server: reject quantity<1 or >5
STEP 1 OF 2

Predict first

An attacker can skip the browser form and send a request containing quantity=1000.

STEP 2 OF 2

Explain

The server must enforce actual constraints; browser checks are useful but only improve convenience.

WE DO · DIFFERENT PROBLEM

A pupil updates their profile photo. Decide which processing belongs in browser versus server.

Client: preview selection and format warning.
Server: verify account, check type/size, store safely.
STEP 1 OF 2

Predict first

The browser can preview or resize an image to reduce traffic and improve usability.

STEP 2 OF 2

Explain

The server verifies authorisation, validates the uploaded bytes and applies safe storage rules.

WORKED ANSWER

WORKED ANSWER

Authentication/authorisation [2], stock update [1], secure payment integration [1], transaction/integrity [1], server-side validation [1].
