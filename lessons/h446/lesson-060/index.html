Lesson 060 · Refining an Abstraction and Testing Assumptions

By the end you can…
  • Compare the simplification against new requirements. If the model omits a relevant factor it can produce plausible but wrong outputs.
  • Refine the abstraction by adding only the newly necessary variable, rather than reconstructing every real-world detail.
  • Test normal, boundary and exceptional cases: 5 km versus 6 km, return and single, and invalid negative distance.

NEW LEARNING · CODE FIRST

Trace the example

// Version 1 ignores return journeys.
decimal Ticket(int km)=>km<=5?2m:4m;
// Version 2 includes return flag.
decimal Ticket2(int km,bool isReturn){
 decimal single=km<=5?2m:4m;
 return isReturn?single*1.8m:single;
}
// For 8 km return: 4×1.8 = £7.20.

I DO · MODEL

A simplified cinema ticket model uses only age but now weekend prices differ. What change is needed?

Add isWeekend as an input and apply weekend rule; retain age category where relevant.
WORKED EXPLANATION

Explain

Weekend becomes a relevant distinction because it can change the output.

WE DO · DIFFERENT PROBLEM

A parking price model charges £3/hour but introduces £12 maximum. Improve algorithm.

fee=MIN(3×hours,12), with validation that hours≥0.
WORKED EXPLANATION

Explain

Cap is new relevant rule. Example 5 hours costs £12, not £15.
